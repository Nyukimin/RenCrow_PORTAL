# PORTAL LIVING heartbeat activity contract

`GET /api/living/heartbeat` is the authenticated PORTAL relay for CORE's read-only `GET /viewer/living/heartbeat`. The LIVING scene polls it while the workplace view is visible and renders the approved activity label in each actor's heartbeat bubble.

CORE owns one canonical current activity Task per actor, including rest, hobbies and off-lease game play. BOARD and LIVING consume that assignment. A waiting game Task may remain current between controller turns; compute admission and activity lifetime are separate. Missing, duplicate or terminal current assignments are errors. Task identity and private titles remain internal to CORE under the existing public-title visibility policy. WORLD remains the source of actual position and seating, so the browser does not place an actor at a PC based on the bubble alone.

CORE may also send `current_activity: {kind, label, phase, revision}` on heartbeat and WORLD HOUSE actors. The object contains only the canonical activity descriptor; it has no Task ID or private title. PORTAL accepts only the fixed activity kinds, their curated Japanese labels and phases, the actor-specific chat/hobby labels, and a positive integer revision. It forwards that same object through the heartbeat and WORLD projections, and the LIVING bubble uses its label ahead of the legacy scheduler label. A missing descriptor remains compatible with older CORE responses; a malformed or unknown descriptor rejects the heartbeat or WORLD snapshot instead of being silently discarded.

Read compatibility includes the exact descriptor `rest / 休憩中 / resting` with a positive revision, even when a newer scheduler stops selecting rest. Removing this vocabulary while CORE still publishes it rejects the complete eight-resident WORLD snapshot and can make LIVING empty; the heartbeat relay can also return 503. Display compatibility does not schedule or generate rest. The regression tests `living_legacy_rest_test.go` and `living_legacy_rest.test.js` cover all eight residents, canonical labels, malformed descriptors, private-field rejection, and recovery after rejection.

The live served validators accepted all eight resident positions and labels, and the heartbeat returned HTTP 200. The upstream compatibility implementation was already present in `f8fe5c2`; this regression coverage preserves that contract. Browser visual verification was unavailable during the repair. Existing pending WORLD movements are a separate runtime issue.

CORE may add `routine_availability: "available"` and `ongoing_activity: "moving_home"` to an actor whose scheduler is `waiting`, or whose active lease is `running` with `activity_kind: "routine"`. CORE requires a persisted pending routine move with a committed, event-verified WORLD receipt and a fresh WORLD snapshot matching the mapped actor, activity ID, private-room target, route ID, and scene hash. The move remains visible after its due time while the exact move is still active and has no verified finish/stop receipt. A missing or failed fresh WORLD read does not project movement.

The PORTAL relay accepts the legacy routine annotation for an available waiting routine actor, and for a running routine actor with `moving_home`, `rest` or `sleep_window`. When `current_activity` is present, its curated label takes precedence over legacy scheduler labels. Receipt IDs, route IDs, scene hashes, room IDs, and raw WORLD details are not exposed by the public heartbeat contract.

CORE projects the seated-rest `ongoing_activity` values only after the corresponding activity checkpoint has started and a fresh WORLD snapshot confirms the actor's exact shared seat and idle seated pose. `sofa_reading` requires the reader's `Read.StartedAt` checkpoint; `sofa_chat` requires `Conversation.StartedAt`; solo `dining_tea` requires `Tea.StartedAt` and the actor's running routine; `dining_tea_chat` requires both participants' exact dining seats, both running routines, and the `Tea.StartedAt` plus `Conversation.StartedAt` checkpoints before the conversation completes. These values are absent before the checkpoint, while moving to a seat, and after pause or completion. `dining_tea` records a virtual tea activity: WORLD has no drinking action, and the label does not assert that WORLD confirmed a drink.

The PORTAL browser accepts these four values only when `routine_availability: "available"` and the scheduler is waiting or running a routine. A waiting actor may omit `activity_kind` or report `"routine"`; a running actor must report `activity_kind: "routine"`. The labels are **ソファで読書中**, **ソファで会話中**, **ダイニングでお茶中**, and **ダイニングでお茶・会話中**. The relay validates and displays the CORE projection; it never infers an activity from a seat alone. BOARD, private, game, foreground, stopping, and other non-routine states keep their existing scheduler label and cannot inherit one of these labels.

For the seated visual, PORTAL forwards only a validated seated-rest value to the scene. The scene selects the existing `read`, `talk`, or `tea` pose only when that value belongs to the same actor whose current WORLD room and shared `seat_id` match the activity and the actor has no active WORLD action. A mismatch falls back to the WORLD `seat_action` or the existing sitting pose. The overlay is render-only: PORTAL does not change `seat_action`, and it clears the activity on the next heartbeat update that omits it. Active WORLD actions and other CORE work keep their existing priority.

WORLD position data remains visible from the last accepted snapshot when a later read fails, but seated-rest poses require a successful WORLD read within five seconds. A failed or timed-out read disables only the pose overlay immediately; the five-second snapshot freshness boundary also disables it if polling stalls. A later accepted snapshot restores the overlay when the CORE heartbeat still reports the matching activity.

The Go relay uses the same four-value allowlist and state rules before returning a heartbeat response. An unknown `ongoing_activity` or a value paired with an incompatible routine state rejects the complete CORE projection with the generic HTTP 503 response; the browser then clears its bubbles. This boundary does not alter the separate `game_id` projection or private-title rules below.

WORLD HOUSE snapshots also carry `active_kind` separately from heartbeat activity. If an actor has both a valid `seat_id` and an `active_kind`, the active WORLD activity takes precedence: PORTAL retains `active_kind` and omits `seat_id` and `seat_action`, so the scene does not render a seated pose for an actor who is moving, sleeping, exercising, or posing. An idle actor may retain a validated seat and seat action.

For a running game actor, CORE may include an optional string `game_id` from its fixed allowlist (`nethack`, `herzog_zwei`, `territory_commander`, `survival_garden`). PORTAL rejects other JSON types and relays only `nethack` as a display ID; the other allowlisted IDs and unknown strings are omitted from its projection. The browser displays **Nethackで遊んでる** only for `activity_kind: "game"` with `game_id: "nethack"`; other or missing game IDs display the general **ゲームで遊んでる** label. Game IDs on other activity kinds do not affect the label. This field does not change the existing private-task title visibility policy.
